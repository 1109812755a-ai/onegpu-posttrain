# 技术设计

## 背景

动机见 `proposal.md`，外部可观察行为见三份能力规格。现有数据构建器已输出确定性的 `ds-*` ID、规范化文件 SHA-256、YAML manifest，以及关联的处理／质量报告。训练命令输出 `run.json`，评测命令输出 `eval.json`，但两者尚未稳定记录跨产物祖先关系。前端目录目前按数据集引用查找关联运行。本设计统一新产物的 Run 身份与图关系，不搬迁大型产物，也不引入服务。

## 目标 / 非目标

**目标：**

- 新来源信息与所描述文件共置，使用统一的 schema／版本和校验状态词汇。
- 将 `experiment_id`（可选实验分组）、`run_label`（可重复展示标签）与唯一 `run_id`（每次实际操作）分开，所有可追溯产物引用 `run_id`。
- 形成来源 → 数据构建／清洗 → 数据及处理报告 → 质量评估 → 训练／合并 → 模型 → 评测及指标的证据链。
- 明确记录证据缺口；本地校验仅证明引用与摘要的一致性，不证明因果效应或数据质量。
- CLI、测试和只读前端都能消费新产物关联；前端不负责写血缘。

**非目标：**

- 为旧 Smoke 运行补造缺失历史；除非另行依据证据迁移，历史产物保持 `legacy`。
- 本次引入数据库、事件总线、调度器、OpenLineage 服务、MLflow 强依赖或 UI 血缘图。
- 在上游未提供时，保证取得数据许可、来源修订或模型摘要。
- 证明清洗步骤导致模型指标变化；因果比较仍需独立的 OVAT 实验设计。
- 本次实现清洗效果归因引擎、`data_effect_report` 或完整实验注册表；未来报告仅引用本次稳定 ID。

## 技术决策

### 1. 文件契约与 schema 演进

新生成的数据集 YAML manifest 增加 `lineage` 区块；新训练的 `run.json` 旁写 `lineage.json`，新评测的 `eval.json` 旁写 `evaluation_lineage.json`。新区块／文件统一使用 `lineage_schema_version: "1.0"`。新 `run.json` 的 `run_id` 语义变更属于破坏性契约变更，不能仅凭旧 `schema_version` 判定新语义；读取器必须依据明确版本／字段判别新旧。数据 manifest 的血缘区块包含 `parents`、`produced_by_run_id`、`transform`、`source_evidence`、`record_provenance`、`count_unit`、`content_sha256`；处理与质量报告有独立 ID、摘要和关联 Run。跨字段不一致时校验失败。文件与模型引用使用 `{id, path_or_uri, sha256, availability}` 加类型专用字段。`inputs.datasets` 保持 `{dataset_id, manifest_sha256, ...}` 列表形态；无 manifest 的输入使用不含伪造 `dataset_id` 的文件证据引用。新读取器将旧产物显式标为 `legacy`，拒绝不支持的未来主版本。

备选方案是用中央注册表替换现有格式；这会增加服务依赖，因此 v1 保持本地文件，但允许新产物的 ID 语义重构。

### 2. 身份、摘要和未知值

数据集 ID 继续由来源／配置／内容的确定性身份生成，并覆盖所有会实质改变输出的转换输入。每次实际的数据构建、质量评估、训练、合并、评测调用生成唯一 `run_id`，贯穿该操作的运行记录及产物引用；`run_type` 枚举为 `data_build`、`quality_assess`、`train`、`merge`、`evaluate`。`experiment_id` 可将受控实验的多次 Run 分组，`run_label` 可承载原 recipe 标签，但两者都不是唯一键，也不参与祖先判断。新 recipe 使用 `run_label` 而非预设 `run_id`；`run_id` 由执行器生成。已有运行产物不可被静默覆盖：目标目录已有运行记录时拒绝复用。评测产物 ID 是独立的 `eval-*`；模型 ID 优先基于已核实的本地输出摘要，否则基于产生它的 `run_id` 和输出角色。已发布 ID 不再改变，不能用时间戳、路径或展示名称证明内容相同。

文件采用流式 SHA-256。模型目录的摘要由按规范化相对路径排序的文件名及各文件 SHA-256 确定，排除自身血缘元数据和临时日志，并记录摘要算法标识。没有本地字节的外部来源／模型使用明确的 `unavailable` 状态加可得仓库／修订证据；摘要计算失败时使用带原因的 `not_computed`。来源修订／许可未知时同样显式标注，不能猜测为 `main`。不得把环境文件中的秘密写入可移植 manifest。

备选方案是给每个运行做内容寻址并下载／计算所有远程基础权重摘要；但操作身份不等于输入集合，强制远程摘要也会破坏轻量、离线的单卡体验。

### 3. 数据来源粒度

扩展构建器对规范化记录的投影：仅在上游提供稳定值时保留 source record／problem／generation ID；偏好对同时保留 chosen 和 rejected 的来源引用。基于稳定来源键及输出角色生成确定性的 `record_id`；缺少来源键时，只生成本地行身份，不把它冒充上游来源。manifest 的 `record_provenance` 标为 `record` 或 `dataset_only`。数据构建 Run 消费源数据／父数据集，产生持久化数据集和处理报告；质量评估 Run 消费确切数据集，产生具有独立 ID、协议版本、检查结果和摘要的质量报告。报告与数据集相互引用时须核对一致性；未生成报告不能视为 PASS。仅持久化的真实清洗中间版本进入图，不为内存状态发明节点。来源许可／条款字段仅记录描述性证据，不代表法律结论。

备选方案是独立的逐条记录事件库；它增加体量与运维复杂度，而 v1 所需追溯能力已可由规范化记录字段提供。

### 4. 运行生命周期与模型 DAG

训练启动前先解析输入模型和数据证据。存在数据集 manifest 时校验 ID、路径和摘要，并建立完整引用；普通 JSONL 无 manifest 时继续允许训练，记录文件路径／SHA-256 和 `incomplete` 原因，不虚构数据集 ID。Mini／OVAT 的正式完整血缘验收要求可验证 manifest，普通 JSONL 路径不能冒充通过。外部／基础模型可缺少本地内容摘要，但本地 manifest 若与输入文件不一致，训练前就应报错。

训练 Run 结束后只登记核实存在的 adapter，adapter 指向父模型和训练 `run_id`。合并是独立的 `merge` Run，消费父模型与 adapter，产生合并模型并有自己的状态、`run_id` 与证据；训练成功、合并失败时不能把两个状态折叠。`PASS`、`OOM`、`FAILED` 均通过收尾路径写各自结果产物，同时保留 CLI 原有退出语义。没有 checkpoint 时输出列表为空；保留的部分 checkpoint 标为 `partial`，不算完成模型。dry-run 仅生成计划证据，不分配代表已执行操作的正式 `run_id`，也不宣称输出模型。不回填旧 Smoke 血缘。

备选方案是仅靠目录名推断父模型，或把存在目录的训练都视为成功；两者都会让阶段比较失真。另一种强制所有训练事先准备 manifest 的做法会破坏现有 `--dataset` 用法，因此将“可以训练”和“达到完整可复现验收”分开。

### 5. 评测来源与比较安全性

保留 `eval.json` 作为指标正文，新增 `evaluation_lineage.json`。每次实际评测有 `evaluate` Run 的唯一 `run_id`；它消费确切模型产物／外部模型描述、基准与留出集证据，产生独立 `eval_id` 的评测产物，记录评测器／协议版本、解析后配置摘要、状态及各指标样本分母。模型来自本地训练时沿模型引用训练／合并 `run_id`。只有真实观测到的结果可标为 `completed`；计划没有最终分数。评测部分完成后失败时保留已知输出并标为部分完成，不补造缺失指标。比较读取器要求基准身份与协议／评分版本匹配，才可无保留地呈现 delta，否则标出不匹配；可用时沿评测 → 模型 → Run → 数据 → 处理／质量报告追溯，缺环则返回完整度状态。

前端可并排展示清洗前后质量分数、模型评测分数和描述性 delta，但不能仅凭这条血缘链标注“清洗带来提升”。因果判断留给后续受控清洗实验：需约束同源样本池、父模型、训练预算、seed 和评测协议，明确唯一变动及不确定性；将来的 `data_effect_report` 通过本次定义的 Dataset／QualityReport／Run／Model／Evaluation ID 引用证据，而非在 v1 实现该报告。

备选方案是从模型文件名或 UI 标签推断来源；这些信息不够稳定，不能支撑阶段比较。

### 6. 校验与集成边界

提供针对指定产物根目录的只读本地校验器，检查 schema、唯一 Dataset／Model／Evaluation／QualityReport ID 与 `run_id`、本地引用、声明摘要、无环的祖先关系及各类型 Run 的输入／输出链接。允许多个 Run 共用 `experiment_id` 或 `run_label`，但不允许复用 `run_id`。报告包含产物路径和 ID 的结构化错误／警告：不可得的外部证据与未登记的普通 JSONL 属于完整度警告，损坏的本地引用属于错误。读取本地引用前先检查路径确在指定根目录内，避免恶意 manifest 让前端／校验器越界读取。前端目录复用共享解析／校验逻辑，保留现有关联运行视图和警告；前端启动不依赖整个图完整。

备选方案是强制元数据后端；v1 的本地可检查文件已经足够，后续仍可映射到 OpenLineage 兼容事件。

## 风险 / 权衡

- [计算本地大型模型目录摘要会增加 I/O 耗时] → 完成后流式计算一次并缓存到血缘；中断时报告 `not_computed`，不假称已验证。
- [旧 recipe 将 `run_id` 当标签，新产物改为唯一执行键] → 配方、CLI、读取器和测试同步迁移到 `run_label`／`run_id`，历史产物标 `legacy` 而非静默重解释。
- [无 manifest 的普通 JSONL 来源不足] → 允许训练、记录文件摘要并降低完整度；Mini／OVAT 验收明确不通过完整血缘条件。
- [外部来源缺少不可变修订／许可] → 带原因显示 `unavailable` 与较低完整度，不编造元数据。
- [部分文件尚未生成就失败] → 实际执行启动时尽早创建 `run_id`，在受保护的收尾路径写血缘；测试 OOM、训练失败与独立合并失败。
- [上游缺少记录 ID] → 只保留核实的来源引用，否则使用 `dataset_only`。
- [摘要验证字节，不验证语义正确性] → 数据质量报告、协议检查与 OVAT 比较独立于血缘有效性。
- [清洗前后数据、质量与分数共现易被误读为因果] → UI／报告仅展示可追溯证据与描述性差异；受控效果判定另行设计和验收。

## 迁移计划

1. 增加新 schema／解析器及测试；旧 manifest、运行和评测只作为 `legacy` 读取，不将旧标签语义映射为新 `run_id`。
2. 同步迁移新 recipe、数据构建／质量评估、训练／合并与评测输出，以及对应读取器；不批量改写现有 `runs/` 或 `artifacts/`。
3. 增加只读校验命令与前端消费检查；新产物进入 Mini 正式验收前须满足完整血缘条件，并能串起清洗与质量证据。
4. 需要回退时停止输出新血缘，同时保留已生成文件；回退不删除历史证据，不能把新旧 `run_id` 混为同一语义。
