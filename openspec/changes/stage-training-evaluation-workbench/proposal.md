# Proposal

## Why

当前 Web Launcher 只开放固定的 Mini SFT 训练与探索性评测；CPT、DPO、SimPO、GRPO 仍需用户切换到 CLI/recipe，逐阶段设置数据和执行流程。用户需要一个按阶段选择已登记数据、训练后继续评测该阶段模型的连续工作台，才能直观看到各阶段改变了什么，同时保持训练、评测和血缘证据一致。

## What Changes

- 提供 CPT、SFT、DPO、SimPO、GRPO 阶段入口；各阶段只列出阶段与用途匹配的已登记训练数据集，启动前展示固定配方、父模型、数据/质量/许可状态和资源预检。
- 为 GRPO 补齐可信训练数据的前端构建/登记入口：抽取可复用的确定性 prompt 构建核心，复用项目批准的 reward 契约和已登记、带允许来源协议及逐条参考答案证据的 train seed；逐条保留来源身份并执行契约、schema、质量与血缘校验。不得接受浏览器上传的任意 reward 插件，也不得把用户自我声明当作参考答案已核验的证据。
- 训练完成且模型产物经核验后，在对应 Run 上提供该阶段适用的评测预检与显式启动；不同阶段使用有版本的评测 profile，分别呈现通用任务指标及可用的阶段专属指标。另提供已登记外部 base 模型的独立网页评测入口，支持数学基准和已登记 evaluation-only 客观题套件。
- 客观题评测结果在汇总分数之外提供逐题报告，可筛选正确、错误和解析失败记录，并对照题目、选项、标准答案及模型答案。
- 训练 Run、产出模型、评测 Run、评测数据集和协议形成可追溯链路；训练失败、OOM、合并失败、评测部分完成等状态如实呈现。
- 保持本地单 GPU、一次一个活动任务、固定批准的 recipe/profile 和 CLI 执行边界；不提供任意命令/路径/参数、不自动开始评测，也不替代 CLI。
- 第一版每个训练阶段选择一个已登记 `dataset_id`；组合数据集可在 `dataset-mixture-composition` 实现后作为普通 dataset ID 被选择，本变更不实现组合逻辑。
- 所有数据构建/导入/生成入口在创建 manifest 时写入以数据集产物根目录为基准的 `canonical_path`；创建时校验路径包含性、文件存在性及 canonical SHA-256，保持旧 manifest 可读但不允许不完整证据通过训练预检。
- 主导航按用户任务收敛为“数据”“训练与评测”“实验 Runs”“分析与改进”：数据统一承接来源、导入/生成、处理、质检与登记；训练负责配置与启动；Runs 提供统一运行详情；分析消费真实结果并发起改进。现有页面迁入对应二级视图，旧链接保留解析。
- 复用现有生成、质检、登记与血缘流程：普通生成从数据入口开始，定向补数从分析带入场景上下文；数据规则编辑归数据处理，策略效果报告归分析，避免重复的配置/执行页面。切换模块或生成方式保留活动任务与可恢复草稿。
- GRPO 数据准备不新增通用/任意 reward 生成器；将确定性构建/登记核心与 targeted-plan 上下文解耦：普通入口不要求诊断方案，后续定向入口可在同一核心上附加方案版本、诊断评测和 holdout 隔离证据。生成/登记后回到 GRPO 阶段并传递精确 dataset ID。

## Capabilities

### New Capabilities

- `stage-training-workbench`: 按阶段选择数据、预检并监督训练，成功后显式启动匹配的阶段评测。

### Modified Capabilities

- `unified-model-evaluation`: 扩展到各 post-training 阶段可用的版本化评测 profile，并明确阶段专属指标与共享基准的覆盖/可比性。
- `web-workspace-ux`: 统一四个主入口、页面职责、上下文交接、任务恢复、旧链接兼容及阶段训练到评测的交互。

## Impact

涉及 `src/onegpu_posttrain/ui/launcher.py`、`server.py`、各阶段 CLI/recipe 与训练适配器、统一评测/阶段专属评估器、数据集 manifest 构建与登记入口、`web/src` 的导航/路由、数据工作台、生成、规则编辑、分析、Launcher/Runs 组件及相应测试和中文产品文档。复用现有 dataset registry、质量报告、模型/run/evaluation lineage；不新增训练框架或数据库。
