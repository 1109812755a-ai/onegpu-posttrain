# OneGPU-PostTrain 产品愿景

**文档状态：** 项目北极星  
**适用范围：** 当前方向及未来路线决策

## 一句话定义

> **从单张消费级 GPU 的开源、可复现后训练实验室起步，最终建设成可部署、能承载真实研究工作流的 Post-Training 平台，让用户理解并可靠运行 CPT、SFT、偏好优化和 RL。**

英文原文：[Product Vision](PRODUCT_VISION.md)。中英文含义一致；产品方向以本文件与英文源文件共同维护。

## 我们在做什么

OneGPU-PostTrain 不是另一个 Trainer 或微调框架。近期形态是开源、可运行的研究基线与学习实验室：让个人工程师在消费级 GPU 上执行完整后训练流程，并检查每个阶段和实验背后的证据。长期终态是可部署的平台级项目：把数据、训练任务、模型、评测、血缘和受控实验组织成完整工作流，支持真实用户持续使用和扩展。

```text
Data → Training → Evaluation → Controlled Experiments
数据 → 训练 → 评测 → 受控实验
```

核心训练关系：

```text
Base → CPT → SFT ─┬→ DPO
                  ├→ SimPO
                  └→ GRPO
```

DPO、SimPO 和 GRPO 默认从同一个 SFT checkpoint 平行分支，以便受控比较；它们不会默认串成一个连续流水线。

## 项目要帮助用户回答的问题

- 每个阶段实际用了什么数据？哪些数据被过滤？应用了什么数据契约？
- 哪一步处理改变了数据的质量和覆盖？受控的下游实验是否观察到相应的模型指标变化？
- CPT 和 SFT 之后模型发生了什么变化？有哪些测量证据支持结论？
- 在数据和控制变量一致时，DPO 与 SimPO 有何不同？
- GRPO reward 上升时，任务能力是否也上升？reward、KL 和 completion 行为说明了什么？
- 改变 learning rate、beta、generation 数量、数据量或 reward 设计会发生什么？
- 为什么训练 loss 下降，benchmark 却可能没有提升？
- 在目标消费级 GPU 上，耗时、吞吐和峰值显存是多少？

## 差异化

差异化不在于“支持 CPT/SFT/DPO/SimPO/GRPO”——成熟训练框架已经提供这些能力。项目贡献在于围绕这些训练方法建立一套可复现、可比较、可解释的实验体系：

- 与数据血缘、分布和泄漏检查并列的阶段化数据质量证据；质量报告公开方法、分母和局限，不隐藏成一个综合分；
- 从来源到最终数据集的有序处理轨迹、可比较的清洗前后质量证据，以及数据集版本到下游模型评测的受控关联；
- 一致的数据血缘和阶段边界；
- 适用时共享任务、领域、偏好和 RL 评测；
- 明确控制变量的 One Variable At A Time 实验；
- 可追溯的 checkpoint、配置、seed、数据集和评测来源；
- 同时报告效果指标与资源成本；
- 诚实呈现限制，不从 smoke 级样本过度推断。

近期体验是**“后训练实验教科书 + 可运行实验室 + 开源研究基线”**；长期要在此基础上成为**可落地的开源 Post-Training 研究平台**，而不是停留在脚本集合或静态演示。

## 产品原则与不变量

1. **单卡优先：** 消费级 GPU 是一等约束和教学场景，不是事后适配项。
2. **开源优先：** 实验定义、接口、实现和证据应可审查；核心流程不依赖专有托管服务；外部贡献者应有清晰参与路径。
3. **观察每个阶段：** 数据、解析后的配置、血缘、训练信号、评测和资源成本应可检查。
4. **受控比较：** 一次改变一个明确声明的变量；按实验问题共享 parent、数据、seed 和评测协议。
5. **证据先于结论：** 区分可行性 smoke 与质量/效应量结论；展示样本量、上下文和缺失测量。
6. **优先 CLI 和成熟训练框架：** 训练继续委托给成熟框架，并保留 CLI 工作流；UI 与编排是辅助层。
7. **实验室是起点，平台是终态：** 先跑通可信的单卡研究闭环，再依据真实使用逐步建设任务调度、实验/数据/模型注册、部署运维与扩展能力；每一层都要服务完整研究工作流。

## 开源产品承诺

- 从公开源码和固定依赖即可在本地使用核心工作流；托管服务集成保持可选。
- 发布足够的配置、数据 manifest/标识、环境、评测协议和 run provenance，让读者能理解并复现结论。
- 明确贡献和扩展方式；主要使用路径不依赖私有服务或未记录的人工步骤。
- 将上游许可与条款纳入数据/模型 provenance。仓库开源不代表第三方数据、权重或生成产物可以再分发。
- 不发布密钥、个人数据或受限原始记录。

## 初期不追求什么

- 替代 ms-swift、TRL 等训练实现；
- 成为通用分布式训练框架；
- 在单卡研究闭环和用户需求尚未验证前一次性建设重型调度器、数据库或分布式平台；
- 缺少复现和 provenance 的排行榜分数；
- 掩盖实验假设、而不是解释实验的 UI 功能。

这些是阶段顺序，不是永久禁令。平台能力会逐项进入路线：先本地受控启动与串行队列，再补稳定的 registry、任务生命周期、部署与资源管理。每项能力都要有真实使用场景、兼容的开源接口和明确的运维边界。

## 演进方向

```text
单卡可复现实验室（v0.1）
  ↓
本地实验启动、OVAT 与串行任务队列（v0.2–v0.3）
  ↓
数据/模型/实验 Registry 与扩展研究（v0.4–v0.6）
  ↓
可部署、可运维、可扩展的开源 Post-Training 平台（v1.0）
```

平台是明确的最终目标，实验室是经过验证的起点。具体部署形态、并发和资源调度方案按用户场景与证据逐步定型，不预设必须采用某个重型基础设施。版本顺序见[项目 Roadmap](../../ROADMAP.md)和[前端路线图](frontend/FRONTEND_ROADMAP_zh.md)。

## 功能决策过滤器

添加功能前先回答：

1. 它解决哪个后训练问题或复现缺口？
2. 它能否改善理解、受控比较、provenance 或单卡执行？
3. 停止使用 UI/服务后，是否仍能通过 CLI/artifact 获得并审查结果？
4. 它引入哪些状态、依赖或运维复杂度？
5. 有什么证据能说明它帮助了目标用户？

如果一个平台功能没有对应的真实工作流、用户和运维证据，就先不进入当前版本；但不能因此丢掉 v1.0 可部署平台的终态目标。
