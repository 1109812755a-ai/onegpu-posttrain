# 前端产品设计

**状态：** Data 浏览、opt-in 本地策略编辑器和定向补数工作台准备切片已有提前交付；完整 UI 仍在实施中。  
**完整目标：** v0.1.1 本地 Experiment UI，包含只读 artifact 浏览和受限本地编辑器；provider 生成/训练仍由 CLI 显式执行。

本 UI 从属于[项目产品愿景](../PRODUCT_VISION_zh.md)：目标是让实验依据更容易检查，而不是把项目变成通用训练平台。

## 产品目标

让 OneGPU-PostTrain 已生成的证据更容易浏览和比较，同时不改变实验的构建和执行方式。UI 应帮助单卡研究者回答：

- 当前有哪些 run 和模型阶段，它们之间是什么关系？
- 阶段是 PASS、OOM 还是失败？判断依据在哪里？
- 任务质量、偏好行为、reward、耗时或显存发生了什么变化？
- 数据筛选在哪些环节损失了样本？有哪些 artifact 可查？

artifact 浏览是本地只读的，不是暗示训练正在实时编排的 Dashboard。独立策略编辑器只有显式启用后才可预览本地数据或保存新的策略/实验草稿，并且不会启动训练。页面必须区分“缺失指标”和 0，也要区分 smoke 可行性证据和质量结论。

## 用户与主要工作流

主要用户是本机检查实验的项目作者或贡献者。

1. 打开 Overview，查看阶段/run 状态、硬件信息和需注意的告警。
2. 按阶段、算法、seed、状态筛选 Runs 并打开某个 run。
3. 查看其配置、parent checkpoint、训练/评测证据、日志和 artifact。
4. 在数据集/协议一致时比较 checkpoint；缺失或不可比的指标要明确标出。
5. 查看数据保留/拒绝原因及 GRPO/Preference 诊断，决定下一步实验。

针对评测驱动的定向补数，UI 提供一条范围受限的工作流：场景证据与分母 → provider/提示词/输出协议草稿 → 生成/验证摘要 → 模型/评测效果摘要。页面导出的是未登记配置草稿，只读取白名单摘要；不得接收密钥值、调用 provider 或启动训练，也不得从候选数/loss/reward 推断能力提升。

## 版本边界

### v0.1.1：本地 Experiment UI

- 读取用户配置的 `runs/` 与 `docs/results/` 根目录下的已有文件；
- 提供 Overview、Runs、Run Detail、Stage Comparison、Data、GRPO/Preference Analysis；
- 不启动/停止进程，不编辑配置，不写入 run 目录，也不把轮询 artifact 误称为实时 run 状态；
- 不引入数据库、账户系统、远程服务或调度器。

### 后续版本

- v0.2 可启动白名单内的本地 recipe，并显示进程状态/日志；
- v0.3 可定义 OVAT 组合、比较多 run/seed 并导出报告；
- v0.4+ 在 provenance schema 稳定后再考虑数据集/模型/实验 Registry 视图。

门槛见[前端路线图](FRONTEND_ROADMAP_zh.md)。

## 建议的实现形态

以下是实现前的默认建议，新增依赖前需 ADR 确认：

- 前端：React + Vite + TypeScript；Ant Design 用于表格/表单；ECharts 用于联动指标和时序图；
- 本地 API：FastAPI，作为只读文件适配层；策略预览/草稿接口需单独显式启用；
- 存储：`runs/` 与 `docs/results/` 中已有 JSON、JSONL、Markdown 和训练日志；v0.1.1 不需要数据库；
- 部署：本地开发进程，默认只绑定 loopback。

后端将不同 artifact 版本规范化为少量 UI schema，不改变训练/评测语义，也不静默改写源文件。

v0.1.1 应在 Overview 和 Run Detail 中只读展示血缘图。首版不要求独立 Registry 风格的图谱浏览页面。策略编辑器只写入专属的新草稿目录，不改写来源数据、run 或评测产物。

## 信任、安全和易用原则

- **任务优先，不是仪表盘优先：** 围绕“跑了什么、改变了什么、原因是什么、证据在哪里”组织内容，不堆满图表。
- **渐进披露：** 先显示状态和关键结论；需要时再展开协议、分母、配置、血缘和原始 artifact，且不丢失当前上下文。
- **就地解释科学含义：** 为指标和阶段术语提供简洁说明；指标方向、单位、样本数和限制要容易找到。
- **导航连贯：** 从比较打开 run 时保留筛选和上下文；提供清楚的返回路径；每个派生结果都能链接回来源。
- **血缘可探索：** 选择节点可查看其 parent/child 和底层 artifact；同时提供键盘可操作的列表/表格作为图形替代。
- **帮助决策，而非装饰：** 比较界面要清晰呈现 baseline、delta、兼容性和缺失证据；不能用视觉强调暗示没有依据的“赢家”。
- **用真实任务做体验验证：** 验证新用户能找到某 run 的 parent/data/evaluation，理解指标为何缺失，并从比较页进入证据，而不依赖聊天记录或隐性知识。
- **交互体验作为发布门槛：** 首要任务路径应能被发现；筛选、详情、返回和来源跳转要保持上下文；长内容分层呈现；加载、无数据、错误、过期和权限拒绝状态应给出可理解的下一步。
- **可访问性与响应式：** 主要操作可用键盘完成，焦点和选中状态清楚；窄屏下核心信息和操作仍可用；图表有表格/列表替代，状态不只靠颜色区分。
- v0.1.1 的 artifact 浏览保持只读；策略编辑仅是显式启用的本地新草稿写入，不控制进程；
- 只访问明确配置的 artifact 根目录；拒绝目录穿越和逃出根目录的 symlink；
- 不因文件位于 run 目录下就开放模型权重、凭据、环境转储或任意文件；只展示白名单类型；
- Markdown 必须作为安全文本/有限 Markdown 渲染，不执行 HTML 或脚本；
- JSONL/日志读取必须分页/限长，标明截断和解析错误；
- 缺失、陈旧、格式错误和尚未生成的数据使用不同状态，不能把缺失指标当作 0；
- 能展示的每个结果尽量给出 run ID、阶段、seed、parent、数据/评测来源及源文件；
- 比较结果必须提示协议/数据不匹配，不得跨不兼容评测计算 delta；
- 键盘操作、可读对比度、响应式布局和空/错误状态均属于验收条件。

## 首版成功标准

- 六个 v0.1.1 页面能读取代表性的真实 smoke artifact，且不改动源文件；
- 每个状态/指标均可追溯，或明确标为派生值；
- 缺失/旧字段、坏文件、大日志和可选 artifact 缺失时都能安全且清楚地呈现；
- 不完整或不兼容的评测不会产生误导性排名；
- 文件访问限制在配置根目录，浏览器不暴露模型权重和秘密；
- UI 启停有文档；UI 关闭后 CLI 仍可独立工作。
- 基于真实用户任务的体验检查确认：证据与限制容易发现、导航上下文得以保留、图表不会遮蔽底层 artifact。
- 用户可在无讲解情况下完成核心任务 walkthrough：从数据集找到处理步骤和质量证据，识别缺失/警告，再追到关联 run；并能筛选、查看详情、返回而不丢上下文。

## 明确非目标

v0.1.1 不做训练调度器、远程多用户部署、RBAC、数据库 Registry、自动 HPO、分布式监控、artifact 上传或 CLI 替代品。
